## Context

This record moves [FY-0005][fy-0005] from [flakeyard/decisions][decisions]
unchanged in substance. Records there that also govern this repository include
[FY-0024][fy-0024] (versioning and support), [FY-0036][fy-0036] (the stable
nixpkgs branch and the order of Nix minor updates) and [FY-0032][fy-0032]
(publication behind an approval).

Development in flakeyard projects happens in a container: Nix and its store live
there, not on the host, and people without Nix on their machine work as if they
had it. The container must work for anyone with a container engine, whatever
they edit with: an IDE that understands the
[Dev Containers specification](https://containers.dev/), the `devcontainer`
command line, or a plain `docker run` with a terminal editor. Other
organizations consume the image through the projects generated by flakeyard
templates and directly.

Prototypes with real tools established:

- Single-user Nix with the store owned by the developer fails: store paths live
  in lower image layers owned by root, and the first `nix shell` fails with
  `fchmodat2 ... Operation not permitted`. A multi-user daemon running as root
  inside the container works with any developer uid.
- An image built with `dockerTools` has no loader or libraries at the standard
  paths of other Linux distributions. Servers that editors install into the
  container at connection time are such binaries. nix-ld at the standard loader
  path runs them.
- A container whose first process is a long-running command without signal
  handling takes ten seconds to stop and accumulates zombie processes.
- A first process that hands over to the init process with `exec` loses a
  `SIGTERM` that arrives during the `exec`: the kernel drops a signal to PID 1
  that has no handler, and the container takes ten seconds to stop.
- The developer's uid on the host varies. Dev Containers tools adapt the
  container user to it when building a derived image; a plain `docker run` does
  not.
- With `includeNixDB`, only `contents` are garbage collection roots; anything
  the image uses outside them is deleted by the first `nix store gc`.
- Rootless Podman maps the host user to root in the container unless started
  with `--userns=keep-id`. With plain `keep-id`, the host user keeps its uid and
  gets its own entry in `/etc/passwd`, so the image cannot adapt `dev` to a host
  uid other than 1000; `keep-id:uid=1000,gid=1000` maps the host user to `dev`
  instead.

## Decision

This repository publishes one generic image, `image-devcontainer`, built with
Nix and containing no project toolchain. Projects get their tools from their own
`flake.lock` through direnv and nix-direnv.

### Contents

The image contains Nix (the C++ implementation), direnv, nix-direnv, bash and
the tools a shell needs before a project shell exists: coreutils, findutils,
diffutils, grep, sed, awk, tar, gzip, xz, bzip2, zstd, less, procps, which,
util-linux, getent, curl, git, the OpenSSH client, CA certificates, time zones
and service names. It does not contain compilers, language servers, debuggers,
profilers, editors, other shells or support for Dev Containers features;
debuggers and profilers come from project shells, and capabilities they need are
set by the project's `devcontainer.json`.

### Start-up

The container starts as root, and the image starts `tini` first: it handles
signals from the start, forwards them to the process group of its child and
reaps orphaned processes. It runs the entrypoint, which:

1. adapts the `dev` user to the owner of the project: to `DEV_UID` and `DEV_GID`
   when given, otherwise to the owner of the working directory when it is a
   mount point not owned by root;
2. starts the Nix daemon, restarts it when it exits, and waits until it answers;
3. runs the command as `dev` in its own place, under `tini`.

Started without root, it warns that Nix is not available and runs the command.

### Nix

Nix runs in multi-user mode: the store belongs to root and is written only by
the daemon, builds run as dedicated build users. The sandbox is off, because it
needs privileges a dev container does not have and would silently fall back;
continuous integration builds with the sandbox on. Only root is a trusted user,
the only substituter is `cache.nixos.org`, and further settings, such as an
opt-in binary cache, go to `/etc/nix/local.conf`, which `nix.conf` includes. Nix
collects garbage by itself when free disk space runs low.

### Foreign binaries

nix-ld is installed at the standard loader path of each architecture, and the
libraries editor servers check for are linked at their standard paths. The
library set is the one those servers actually need, measured with `readelf`.

### Dev Containers

The image carries the settings it needs in its `devcontainer.metadata` label:
`remoteUser: dev`, `overrideCommand: false`, `init: true`,
`updateRemoteUserUID: true`. A project's `devcontainer.json` needs only the
image reference. Templates may add `postCreateCommand: direnv allow` and named
volumes for state under the home directory that should survive recreation of the
container, such as caches and editor servers.

### Distribution

The image is published to `ghcr.io/flakeyard/image-devcontainer` for
`linux/amd64` and `linux/arm64` as one manifest list, built natively on each
architecture, with provenance attestations. Tags `vX.Y.Z` are immutable, `vX`
points to the latest release of major version `X`, and there is no `latest`.
Consumers reference the image by digest.

### Engines

Supported are Docker, the Dev Containers tools, and rootless Podman 4.3 or later
with `userns = "keep-id:uid=1000,gid=1000"` set in the user's own
`containers.conf`. A shared `devcontainer.json` cannot carry that option,
because Docker rejects it. The entrypoint and the Nix daemon need the
capabilities `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID` and `SETGID`, which
Docker and Podman grant by default; without `FOWNER`, builds cannot set the
permissions of their outputs.

## Constraints

### Build and distribution

- The image MUST be built from a `flake.lock`-pinned nixpkgs with
  `dockerTools.streamLayeredImage`, and rebuilding the same commit MUST yield
  the same image digest.
- The image MUST be published for `linux/amd64` and `linux/arm64` as one
  manifest list, built natively per architecture, with provenance attestations
  for the index and every platform manifest.
- Tags `vX.Y.Z` MUST be immutable, `vX` MUST move with releases, and `latest`
  MUST NOT exist. Cleanup of registry versions MUST NOT delete platform
  manifests or attestations of a tagged image.
- Consumers MUST reference the image by digest; templates MUST emit
  `ghcr.io/flakeyard/image-devcontainer:vX@sha256:<digest>`.
- Every store path the image uses outside `contents` MUST be a garbage
  collection root.
- The image size MUST be tracked in CI against a recorded budget; exceeding it
  MUST fail the build until the budget is raised deliberately.

### Entrypoint

- The image MUST start as uid 0, and its entrypoint MUST:
  - validate `DEV_UID` and `DEV_GID` as decimal numbers and refuse 0 and
    identities that belong to another user or group;
  - adapt `dev` to the owner of the working directory only when it is a mount
    point owned by a non-root uid;
  - change ownership only of files on the home directory's own filesystem, never
    of mount points or mounted files; apart from them, it MAY give `dev` the
    anonymous pipes and sockets and the container's own terminal that the engine
    passes as standard input, output and error;
  - run the Nix daemon supervised and report when it does not answer;
  - run the command as `dev` under an init process that reaps children and
    forwards signals.
- That init process MUST be the first program the image starts and MUST run the
  entrypoint, so that no signal arrives before it handles them.
- Started without uid 0, the entrypoint MUST print a specific warning and still
  run the command.
- Settings the image requires from `devcontainer.json` MUST be carried in its
  `devcontainer.metadata` label; consumers MUST NOT be required to repeat them.

### Nix daemon and trust

- Nix MUST run in multi-user mode with build users; the store MUST stay owned by
  root and MUST be written only by the daemon.
- Only root MUST be a trusted user. The default substituters MUST be limited to
  `cache.nixos.org`; other substituters and keys MUST come only from
  `/etc/nix/local.conf`. The image MUST NOT set `accept-flake-config`.
- `sandbox` MUST be off in the image and the reason documented; builds that must
  be isolated MUST run in CI.

### Image contents

- The image MUST NOT contain project toolchains, language servers, debuggers,
  profilers, editors, shells other than bash, or support for Dev Containers
  features. Project tools MUST come from the project's `flake.lock` through
  direnv and nix-direnv.
- Foreign binaries MUST be supported through nix-ld at the standard loader path
  of each architecture. The library set MUST be derived from the binaries it
  serves and enforced by the smoke test.

### Testing and public API

- Smoke tests (the daemon, direnv and a project shell, an editor server
  starting, ownership of files in a bind mount, both architectures) MUST run
  only in the CI of this repository and MUST NOT be executed in consumer
  projects.
- The public API of the image, where every incompatible change is a major
  release, is: the user name `dev` and its home `/home/dev`; the meaning of
  `DEV_UID` and `DEV_GID`; the behaviour of the entrypoint; the environment
  variables it sets; the `nix.conf` settings and `/etc/nix/local.conf`; the
  `devcontainer.metadata` defaults; the list of tools by name; the Nix
  implementation and its minor version; supported platforms and engines;
  required capabilities. Versions of other tools MUST NOT be treated as API.

## Consequences

- (+) One image for every editor and engine; project tools are pinned by the
  project, not by the image.
- (+) Files created in the project belong to the host user without per-user
  images or manual flags.
- (+) Fast stop, no zombie processes, and a Nix daemon that survives crashes.
- (+) A project's `devcontainer.json` is one line.
- (−) The container starts as root, and `docker exec` without a user is root and
  trusted by Nix.
- (−) The store lives in the container: recreating it means downloading project
  shells again, which the binary cache keeps short.
- (−) Builds inside the container are not isolated from each other.
- (±) nix-ld and its library set must keep up with the binaries editors ship;
  the smoke test tells when they do not.

## Alternatives considered

- **Single-user Nix owned by the developer.** Fails on store paths in lower
  image layers owned by root.
- **A distribution base image with Nix installed on top.** Foreign binaries and
  Dev Containers features work natively, but the image depends on a second
  package manager and is not reproducible from `flake.lock`. Kept as the
  fallback if an editor's server needs more than nix-ld provides.
- **A tree of libraries at standard paths instead of nix-ld.** Still needs a
  loader shim; two links in `/usr/lib` already cover what editor servers check.
- **A named volume for `/nix`.** Survives recreation, but hides store updates
  shipped with a new image and needs versioning of the volume.
- **Relying on consumers to pass `--init` and settings in their
  `devcontainer.json`.** Every consumer would have to know them, and a plain
  `docker run` would still stop slowly and leak zombie processes.
- **One image per project with the project shell inside.** Starts instantly but
  needs a new image for every lock update.
